# 군단 Cloudflare 메모리 전투 서버

영향 범위: 한판 군단의 새 경기만 선택적으로 별도 Worker/Durable Object에 연결한다. 기존 Sites 프로젝트 ID, D1/R2 바인딩, 미로 서버와 다른 게임은 유지한다. 별도 `realtime-swarm/wrangler.jsonc`가 방당 하나의 SQLite-backed Durable Object를 선언한다. 최초 배포 전 Cloudflare 계정 연결이 필요하다.

Sites와 전투 Worker에 같은 `SWARM_REALTIME_SECRET`을 비밀 값으로 설정하고, Sites에 `SWARM_REALTIME_URL`을 설정한다. 키와 토큰은 Git에 저장하지 않는다. 새 경기 시작에서 연결 가능한 서버를 확인하고 전송 방식을 고정한다. 진행 도중 D1과 메모리 서버를 섞지 않는다. 한판 HttpOnly 쿠키로 현재 참가자를 확인한 후 짧은 연결 티켓을 발급한다. 한 방의 좌석·모드·라운드는 서버가 결정한다.

Sites의 `SWARM_REALTIME_ROOMS`가 빈 값이면 새 방식은 비활성이다. 처음에는 직접 만든 검증방 코드만 쉼표로 지정해, 실제 사용자 경기에 영향을 주지 않고 비교한다. 공개 서버에서 평균과 p95 모두 개선되고 세 모드·재접속이 통과한 뒤에만 `*`로 전체 새 경기에 적용한다. 비워도 이미 선택된 DO 경기는 같은 서버에서 끝까지 진행한다.

전투는30Hz, 상태 전송은 기존10Hz로 시작한다. 매 프레임 D1 읽기·잠금·저장을 하지 않는다. DO 저장소에 복구용 체크포인트를 보관한다. 부모 방의 현재 라운드와 참가 상태를 주기적으로 확인해 이전 경기 입력과 퇴장한 좌석을 닫는다. 재접속은 같은 좌석과 명령 번호를 복구한다. 배포 비교가 악화되면 새 경기의 활성화를 끄고 이전 배포로 복구한다.

Workers Free의 SQLite-backed Durable Objects를 우선 사용한다. 유료 플랜 전환은 이 구현의 일부가 아니다. 실제 계정 배포와 공유방 성능 비교 전에는 공개 서비스 개선 완료로 보고하지 않는다.

## 현재 검증과 남은 작업

로컬의 실제 workerd/SQLite DO에서 고정 좌석·공유 강화·중복 비용 방지·서버 재시작 후 상태/명령 번호 복원·퇴장 좌석 차단을 확인했다. 한판 API와 별도 Worker를 연결해1대1/팀전/개인전의 쿠키 인증, 연결 티켓, HTTP와 DO의 이중 진행 차단도 검사했다. 전송 선택과 명령 경로를 포함한23개 검사, 기존 군단 통합131항목이 통과했다. 전체 TypeScript의 기존54개 오류는 남아 있고 신규 군단 경로 오류는 없다.

Cloudflare 계정이 아직 없으므로 실제 계정의 Worker/DO 배포와 활성화는 진행하지 않았다. 가입·로그인·Wrangler 연결 후 별도 Worker를 먼저 배포하고, 검증방만 활성화해 기존 HTTP 전투와 같은 입력 표본으로 비교해야 한다. 악화되면 검증방을 종료하고 allowlist와 Sites 배포를 이전 상태로 복구한다. 개선되면 `STATE_PATCH_MS`를100에서50으로 바꿔 한 번 더 비교하며, 평균/p95·상태 간격·전송량이 악화되지 않을 때만 채택한다. 로컬 임시 터널의0.1초를 Cloudflare 운영 성능으로 간주하지 않는다.
