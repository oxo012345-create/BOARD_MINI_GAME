# 군단 입력과 보조 조회 추가 최적화

2026-11-03. 개인별200기, AI, 전투 수치와 기존 이동 보간은 유지한다.

## 변경

- 이동/점령/강화 명령의 유효성 검사 후, SQL인증·고정 좌석 확인·64개 대기열 검사·중복 방지 삽입·틱 잠금·체크포인트 조회를하나의D1 트랜잭션으로 묶었다. 진행 가능한 요청은 입력1회+커밋1회로 최대2번의DB왕복이며, 다른 요청이 계산 중이면1회에 명령을 대기열에 남긴다. 기존 경로는 최대4회였다.
- 올바른 부모 방·현재 경기·활성 참가자·고정 좌석이 모두 일치해야 삽입/잠금이 가능하다. 잘못된 좌석/이전 경기/잘못된명령은 DB를 변경하지 않는다. 클라이언트가 주장한 플레이어번호는 사용하지 않는다. 꽉 찬 대기열에서도 동일sequence재시도는 중복 없이 인정한다.
- 군단 전투 중 부모 방의 변경 감시는 단일 조회를1초 간격으로 사용한다. 기존 일반 감시의300ms 간격과 매번 반복하던 테이블 생성 확인/리비전 조회를 피한다. 방장 이동·대기실 복귀·세션 변경은 계속 전달한다. 다른 게임의 감시 경로/주기는 유지한다.
- 군단 전투의 부모 화면 시계 갱신은100ms에서1000ms로 변경한다. iframe내 게임의30Hz 진행/그리기/입력 빈도는 유지한다. 다른 게임의 시계는 기존100ms다.

## 공개 서버 비교 방법

각각의 독립 쿠키로4인 검증방에 접속해, 실제 한판 화면처럼 참가자마다 부모 방long-poll 감시를 함께 켰다.4라운드 동안 각 참가자가 동시에 강화 명령을 보냈다(총16개). 모든 명령은 해당 좌석에한 번만 적용되고 나머지3명에게도 확인돼야 한다. 테스트방은 종료/퇴장 처리하며 쿠키를 결과 파일에 저장하지 않는다.

수정 전 표본: 명령HTTP응답 평균502ms/p95772ms, 명령 승인 평균943ms/p951311ms, 다른 참가자에게 강화가 보일 때까지 평균943ms/p951310ms였다.16/16개 모두 승인·공유됐고 오류는 없었다. 이는 한 PC회선·소규모 병력·짧은 표본으로800기 부하나 실물 휴대폰GPU/발열 검증이 아니다. 최종 배포 후 같은 스크립트/조건으로 다시 측정한다. HTTP응답·명령 승인·상대 상태 반영을 구분하며 디스플레이 지연은 포함하지 않는다.
